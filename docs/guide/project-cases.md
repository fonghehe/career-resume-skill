# 补充项目事实

可以直接补充公司归属、职级日期、本人负责模块和关键阶段。智能体更新项目卡和统计，不要求每个项目都写技术案例。下面是需要深入整理某个技术问题时的参考。

## 从最有把握的项目开始

```text
这次只整理 P01。
请先读取已有项目卡和来源，列出已知事实。
第一轮只问业务背景、使用者以及我负责的具体部分。
等我回答后，再逐步问技术实现、问题排查、方案取舍与结果。
没有得到确认的推测保留在待确认区，不写入已确认贡献。
```

智能体不必一次问完全部问题。一次恢复一个明确事件，通常比要求你概述整个项目更容易找到有价值的细节。

## 按这个顺序恢复上下文

| 阶段 | 本轮最值得回答的问题 | 保存位置 |
|---|---|---|
| 背景与角色 | 谁使用？解决什么业务问题？我负责哪部分？ | 项目卡背景、角色与贡献边界 |
| 实现与协作 | 数据怎样流转？这个技术具体解决什么问题？谁负责其他部分？ | 架构、技术实现、协作 |
| 具体问题 | 哪次问题最难？表现是什么？当时有什么约束？ | 技术案例的问题、约束、分析 |
| 方案取舍 | 我如何定位？为什么选这个方案？放弃了什么？ | 方案、备选、取舍 |
| 结果与复盘 | 如何确认有效？有什么证据？现在会怎样改进？ | 结果、证据、复盘 |

例如“做过实时控制台”不能直接升级为“设计高并发实时架构”。继续恢复订阅方式、消息顺序、重连后的状态同步、取消订阅和生产故障处理；只记录本人确实做过的部分。

## 把确认沉淀成稳定文件

项目卡放在 `local/references/projects/`，第一行使用 `# P01｜项目名称`，索引链接该文件。已有编号保持稳定；后来补充更早的项目也不重排全部编号。

每条贡献保存：状态、本人动作、原因或机制、结果、来源与确认日期。条目可以使用 `P01-A`；它的前缀必须属于当前项目。

技术案例可以放在 `local/references/career/cases/P01-reconnect.md`，并从履历入口或项目卡链接该案例。`build_career.py` 会递归收录 `local/references/career/` 中的 Markdown 正文，补充后重建即可看到更新。至少恢复：案例名称、时间、项目、业务背景、技术背景、问题、原因、方案、选择原因、备选、取舍、结果和重新做一次的改进。不知道就写【待补充】，来源不足时写【暂无外部证据】。

```text
请把本轮确认更新到 P01 项目卡和技术案例库，附来源与确认日期。
同步项目索引、待确认问题与能力证据链接。
我没有确认的结果数据不要补写。
列出本轮新增事实、仍待确认的信息与改动文件。
```

## 从案例抽取可迁移能力

先关联案例，再描述能力。例如“处理重连后的状态恢复”可能支持实时数据处理经验；仅看到 `WebSocket` 标签不足以支持这个判断。

能力地图记录使用项目、最复杂案例、设计责任、生产问题和证据强度，再区分核心能力、熟练能力、实际项目经验、有限项目经验或学习阶段。缺少证据时暂不定级。

职责成长也根据实际变化记录：完成需求、独立负责模块、解决复杂问题、承担技术决策、跨团队设计。正式 Title 不能自动证明相应职责。

完成一个项目后，更新事实与索引，用 `scripts/build_career.py` 重建文字履历。需要网页时按[生成个人网页](generate-webpage.md)刷新展示；若有代码记录，再按[Git 活动](git-timeline.md)补证据。之后可[根据履历生成简历](generate-resume.md)。
